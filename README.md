# Joe Vernazza

The source for [joevernazza.com](https://joevernazza.com): a custom WordPress block theme, a must-use plugin for site behavior, custom blocks, a Vite build, coding standards in CI, and deploys that only ship our own code.

## How this site was built

This repository was generated by **`wordpress-install`**, a reusable [Claude Code](https://claude.com/claude-code) skill I built with Claude Code. Instead of setting up each new WordPress project by hand, the skill turns one well-built site into a template. A single command then produces a new project with the same theme architecture, tooling, accessibility setup and deploy pipeline, already installed and running in Docker.

### Where the skill came from

1. **Static page.** joevernazza.com started as a single hand-written PHP page, with SCSS and JavaScript compiled by Vite.
2. **WordPress rebuild.** I rebuilt it on WordPress to show how I build WordPress sites properly. It started from Twenty Twenty-Five and was reworked into a custom pages-only block theme plus a must-use plugin, with the improvements listed below.
3. **Generalized into a skill.** The finished build was turned into a template, with the site name, slug, PHP prefix, URLs, ports, PHP version and database engine as placeholders. A Node script (`create-site.mjs`, no npm dependencies) fills them in and installs everything.
4. **Reinstalled from the skill.** This repo was then cleared and rebuilt from the skill, keeping the git history, so the site you see is exactly what the skill produces.

### What the install did

```bash
node create-site.mjs --dir joevernazza.com --name "Joe Vernazza" \
  --slug joevernazza --prefix joevernazza --tagline "Senior Front-End Developer" \
  --prod-url https://joevernazza.com --gtm GTM-XXXXXXX \
  --php 8.4 --db mysql --db-version 8.4 --port 8090 --pages-only
```

1. Copied the template and filled in the placeholders. It removes code for features that weren't chosen, and fails if any placeholder is left unfilled.
2. Ran `npm install` and `npm run build` (Vite for theme assets, `@wordpress/scripts` for blocks), and `composer install` for PHPCS.
3. Pulled the Docker images and **pinned each one by digest** in `docker-compose.yml`, then started the containers.
4. Used WP-CLI to install WordPress, then:
   - activated the theme and removed Akismet, Hello Dolly and extra default themes;
   - set Post-name permalinks and wrote the caching rules to `.htaccess`;
   - created the Home, About, Contact and Accessibility pages from the theme's patterns, and the Main menu.
5. Checked that the homepage renders with no PHP errors.
6. Ran the accessibility test (axe-core, WCAG 2.2 AA, desktop and mobile, plus keyboard checks). It passed with no violations.

### Adjustments made along the way, and why

Each of these came from building and testing this site. They now live in the template, so every future project starts with them.

**Architecture**

| Change | Why |
| --- | --- |
| Moved the Vite build into `build_tools/`, writing into the theme's `assets/` | Keeps Node tooling out of the web root and out of deploys. The theme gets plain, fixed-name CSS/JS files that `functions.php` enqueues, versioned by file modification time so each build busts the cache. |
| Replaced Twenty Twenty-Five with a custom theme (own prefix and text domain, only five templates, own patterns, no stock style variations) | A renamed default theme isn't a custom theme. Removing about 100 unused patterns and templates makes the code small enough to read and maintain. |
| Removed the full-page patterns (Home, About, Contact, Accessibility) and kept only section patterns | Any full-page pattern makes WordPress open a "Choose a pattern" screen every time a page is added. Pages here are built from sections, so the screen only got in the way. |
| Moved site behavior into a **must-use plugin** | The theme handles presentation and plugins handle behavior. A must-use plugin can't be deactivated, so security, SEO and pages-only mode survive a theme switch. |
| **Pages-only mode**: posts, comments, feeds, pingbacks and their admin screens are removed | This is a brochure/portfolio site. Leftover blog features add attack surface (comment spam, pingbacks, XML-RPC), clutter the admin, and leak empty archives and feeds to search engines. |
| Design tokens in `theme.json`, with SCSS reading WordPress's generated CSS custom properties | One source of truth, so the editor and the front end can't drift apart. Editors can only pick palette colors, which keeps contrast in check. |
| Custom blocks are built with `@wordpress/scripts` and registered from the plugin | It's WordPress's own block toolchain. The blocks are dynamic (`render.php`), so changing their markup later never triggers "invalid block" errors in the editor. |
| **Site Settings** screen (Head, Header, Footer) | Site-wide values such as the GTM ID, verification tags, contact details and social links are edited in the admin, not in code. That keeps the GTM ID out of the repo and lets content changes skip a deploy. All fields are declared in one list, which drives the screen, the sanitizing and the storage. |

**Repository and deployment**

| Change | Why |
| --- | --- |
| Git tracks WordPress core alongside the theme and must-use plugin; `wp-config.php`, `.htaccess` and uploads are ignored | One push sets up a fresh server, and every environment runs the exact same core. Credentials don't belong in git, and uploads are content. |
| The deploy `rsync`s core, our two folders and each plugin committed to `wp-content/plugins/`, with `--delete` limited to `wp-admin/`, `wp-includes/`, our folders and each committed plugin's own folder | Removed files disappear from the server, but `wp-config.php`, `.htaccess`, uploads and plugins that aren't in git can never be overwritten or deleted by a deploy. |
| Automatic updates are off (`AUTOMATIC_UPDATER_DISABLED`), and wp-admin can't update or install (`DISALLOW_FILE_MODS`) | Core is in git, so an update made on the server would be undone by the next deploy. Updates are done locally, checked, committed and pushed. |
| Lint runs before every build (PHPCS with WordPress Coding Standards, ESLint, Stylelint), and on pull requests too | Coding standards are enforced, not just recommended, and a lint failure blocks the deploy. |
| Docker images are pinned by digest | Every machine runs exactly the same versions until someone deliberately updates them. |
| A sample production `wp-config.php` and `pull-db.sh`/`pull-uploads.sh` scripts | Environment settings stay on the server, documented. Content flows production → local, and code flows git → production. |

**Server parity**

| Change | Why |
| --- | --- |
| PHP 8.4 locally and in CI | It matches the production server, so nothing behaves differently after deploy. PHPCS still checks compatibility down to PHP 8.1, keeping the code portable. |
| MySQL 8.4 LTS, not 8.0 | It matches production, and MySQL 8.0 reached end of life in April 2026. |
| Database scripts use the database container's own `mysql`/`mysqldump`, not `wp db` | WP-CLI ships MariaDB's client tools, which require TLS and can't log in to MySQL 8. I tested relaxing MySQL's login and TLS settings, and the client still refused. Using the server's own tools always matches its version. (MariaDB was tried along the way too; the skill supports both, via `--db`.) |
| The install checks the database through PHP `mysqli` | That's the connection WordPress itself uses, so the check works on every engine and version. |

**Security and SEO**

| Change | Why |
| --- | --- |
| XML-RPC off, file editors off, REST user enumeration hidden, one login error message for every failure, security headers | These close the common WordPress attack paths a small site doesn't need. |
| The pages-only redirect runs before core's canonical redirect | Testing found that `/?author=1` first redirected to `/author/<username>/`, leaking the admin login. Running first sends it straight to the homepage. |
| A lightweight SEO module (meta description from the page excerpt, Open Graph tags, JSON-LD) that steps aside if an SEO plugin is installed | It covers the essentials without a heavy plugin, and won't output duplicate tags if one is added later. |
| Browser caching rules are written into `.htaccess` between their own markers | Core manages its rewrite rules the same way, so the rules survive permalink flushes and can be updated by bumping a version number. |

**Accessibility (WCAG 2.2 AA)**

| Change | Why |
| --- | --- |
| The skip link moves keyboard focus onto `<main>`, not just the scroll position | `<main>` isn't focusable by default, so focus stayed on `<body>` and some screen readers didn't announce the jump. The automated keyboard test caught this. |
| A 2px focus ring on every control (white on dark backgrounds), plus forced-colors support | Visible focus is required (WCAG 2.4.7/2.4.11), and the ring needs 3:1 contrast against whatever it sits on, including in Windows High Contrast. |
| Menu items and buttons are at least 44px tall, using a selector specific enough to beat core's navigation CSS | This exceeds WCAG 2.5.8's 24px minimum. The first version lost to core's more specific selector, which left the focus ring misaligned. |
| Scroll-reveal content is visible without JavaScript, and reduced motion turns off animation and smooth scrolling | Content never depends on a script running or on motion people have asked to avoid. |
| An automated accessibility test (`npm run test:a11y`) that runs on every install, and a footer link to an Accessibility statement page when one is published | The test runs axe-core on every page at two widths, plus keyboard checks, so regressions surface immediately. The statement tells visitors the target and how to report problems. |

## Architecture

**The theme handles presentation, plugins handle behavior.** Switching themes should change how the site looks, never what it does.

- **Theme ([`public_html/wp-content/themes/joevernazza`](public_html/wp-content/themes/joevernazza))**
  - `theme.json` is the single source of design tokens: color palette, the self-hosted Inter font (weights 300, 500 and 700, each with italic), a fluid type scale and spacing. SCSS reads the CSS custom properties WordPress generates from it.
  - **Front end: no WordPress global styles.** `functions.php` removes `<style id="global-styles-inline-css">` and outputs only its CSS custom properties (`--wp--preset--color--*`, font sizes, font family, spacing, content width) as `joevernazza-wp-variables-inline-css`. The element styles (body, headings, links, buttons), preset classes (`.has-*-color`, `.has-*-font-size`), layout rules (`.is-layout-flex`, block gap) and root padding from `theme.json` don't reach the front end; the SCSS styles everything, reading the variables. The editor still loads the full global styles (with `!important` stripped).
  - SCSS (`build_tools/src/scss`): `mixins/` holds the shared helpers (the `mq()` media query mixin in `_breakpoints.scss`: `mq(tablet)` = 768px+, `mq(desktop)` = 1024px+; the color variables and `$colors` map in `_colors.scss`), forwarded by `mixins/_imports.scss`. `global/` holds the site-wide base and `components/` holds styles per component (one partial per block); each folder's `_imports.scss` lists its files. Every file starts with `@use "mixins/imports" as *;` (works from any folder), so `mq()` and the color variables are available everywhere; block SCSS gets that line automatically (`build_tools/scss-globals.js`).
  - Templates: `front-page`, `page`, `page-no-title`, `single-portfolio` (a portfolio entry: Page Pagination, then `<main>` holding the entry's content again in `div.main__text` (core Post Content with that class) and the Portfolio Slider; the entry's title, brand and content are in Sticky Left Side), `index` and `404`.
  - The site header is the **Sticky Left Side** template part (`parts/sticky-left-side.html` → `patterns/sticky-left-side.php`), placed before `<main>` in every template and edited in Appearance → Sticky Left Side. On the front end the theme removes core's `<div class="wp-block-template-part">` wrapper around it, so it's `.wp-site-blocks > .container > header.sticky-left-side`. Every template wraps the header and `<main>` in a Group named "Site container", which the theme outputs as a plain `<div class="container">` (no `wp-block-group` or layout classes); the footer comes after it, outside the container (`.wp-site-blocks > footer`). The footer links to the Accessibility and Privacy pages when they're published.
  - Section patterns in the "Joe Vernazza" category: Hero, Text section and Call to action. There are deliberately no full-page patterns: WordPress shows any full-page pattern in a "Choose a pattern" screen every time a page is added.
  - Editor-only CSS in `assets/css/editor.css` (hand-written, not built) makes all text in the editor canvas black, whatever its colour on the front end. The front end never loads it.
  - JavaScript (`build_tools/src/js`, bundled by Vite into `assets/js/main.js`): `main.js` imports small services and starts them: `animate.js` (scroll reveal: elements with `animate`, or text in an `is-style-reveal` Group, get `animate-active` as they come into view; its own class, so it never clashes with the hover/current `active`), `a11y.js` (skip-link focus) and `navigation.js` (`initMenuToggle()`: the Sticky Left Side hamburger; `initNavigation()`: each `.projects__item`, `.button` and `.menu__item` gets the `active` class while the pointer is over it or keyboard focus is inside it; `initSectionNav()`: Menu links to a `#id` on the page scroll smoothly to that section, and the `.menu__item` of the section that has reached the top of the screen gets `active` and its link `aria-current="true"`).
  - The **"Reveal on scroll"** block style on Group and Separator blocks fades a section's content in as it scrolls into view.
- **Must-use plugin ([`public_html/wp-content/mu-plugins`](public_html/wp-content/mu-plugins))**: always loaded, can't be deactivated, survives a theme switch.
  - `pages-only.php`: removes posts, categories, tags, comments, pingbacks and feeds from the admin, front end, sitemap and block inserter.
  - `security.php`: disables XML-RPC and the file editors, hides REST user enumeration, uses one login error message for any failure, and sends security headers.
  - `seo.php`: meta description (from the page excerpt), Open Graph/Twitter tags, `WebSite` JSON-LD. Steps aside if a full SEO plugin is installed.
  - `site-settings.php`: **Settings → Site Settings**, editable site-wide fields grouped as Head (GTM ID, Google/Bing verification, custom head code), Header (empty, ready for fields) and Footer (a "Hide footer" checkbox that removes the footer from every page, footer text, contact details, social links). Fields are declared once in `joevernazza_site_settings_fields()` (or the filter of the same name), which drives the admin screen, sanitizing and storage. Read values with `joevernazza_site_setting( 'key' )`.
  - `portfolio.php`: the **Portfolio** post type (admin menu → Portfolio). Each entry has a title, block-editor content, an excerpt, a Featured image (the Projects block's thumbnail), an Order field, and role, brand, launch-link and slider-image meta. Role and brand are edited in the entry's **Project details** sidebar panel and slider images in its **Slider images** panel (both part of the Portfolio Slider block's editor script); the launch-link panel was removed with its block, but that meta and the helpers (`joevernazza_portfolio_role()`, `joevernazza_portfolio_brand()`, `joevernazza_portfolio_launch_links()`, `joevernazza_portfolio_slides()`, `joevernazza_slide_picture()`) remain:
    - **Role**: your role on the project, shown after the brand in the header. Stored in `_joevernazza_role`.
    - **Brand**: the brand name. Stored in `_joevernazza_brand_name`.
    - **Launch site**: any number of launch links (for an entry that groups several sites), each with link text (default "Launch site") and a URL. Links can be reordered or deleted; a link without a URL isn't shown. Stored in `_joevernazza_launch_links` as `[ { text, url } ]`.
    - **Slider images**: add as many slider images as you like. Each one is a group of Desktop (1024px and up), Tablet (768–1023px) and Mobile (below 768px) images, stored in `_joevernazza_slider_images` as `[ { desktop, tablet, mobile } ]` attachment IDs. A missing version uses the nearest one that's set.
    - Entries live at `/portfolio/<slug>/`; there's no archive. An entry's first Desktop slider image is its sharing image (`og:image`) when it has no featured image.
  - `analytics.php`: Google Tag Manager, only when `WP_ENVIRONMENT_TYPE` is `production` and a container ID is set in Site Settings. A `JOEVERNAZZA_GTM_ID` constant in `wp-config.php` overrides it.
  - `htaccess.php`: browser caching and compression rules in `.htaccess`, between their own markers.
  - `svg-uploads.php`: lets **administrators** upload SVGs. Each file is cleaned on upload with [`enshrined/svg-sanitize`](https://github.com/darylldoyle/svg-sanitizer) (scripts, event handlers and `javascript:` links removed; unreadable files rejected), and its width and height are read from the file so `wp_get_attachment_image()` outputs real dimensions. Other roles can't upload SVGs. The library is the plugin's own Composer dependency: `mu-plugins/joevernazza/composer.json`, installed into its `vendor/` (git-ignored) with `composer install --no-dev -d public_html/wp-content/mu-plugins/joevernazza`, locally once and by the deploy workflow on every deploy. Without `vendor/`, SVG uploads stay off.
  - `blocks.php`: registers every block built into `joevernazza/blocks/`.
  - `template-part-links.php`: adds Appearance → Sticky Left Side and Appearance → Footer, which open those template parts directly in the Site Editor.
- **Blocks ([`build_tools/src/blocks`](build_tools/src/blocks))**: one folder per block, built with `@wordpress/scripts`. Blocks put their contents directly in the block's outer element, with no inner `.container` (see [`docs/blocks-and-markup.md`](docs/blocks-and-markup.md)).
  - Block CSS (`style.scss`) loads **only in the editor** (`editorStyle` in `block.json`). On the front end each block is styled by its theme partial in `build_tools/src/scss/components/` (`_<block-name>.scss`), so there's one source of front-end CSS and no block stylesheets to override.
  - `section` wraps any blocks in a `<section>`, with no inner wrapper. The HTML anchor (id) and custom classes are set in the Advanced panel. Copy it to start a new block.
  - `button-link` is a link styled as a button: `<div class="button">` (the block's wrapper, with its anchor and custom classes) with `<a class="button__link">` directly inside, no `<p>`. After the text the link holds a decorative arrow, `<img class="button__icon" alt="">`, from the theme's `assets/images/arrow.svg` (looked up at render time by `joevernazza_button_link_icon_url()` in `inc/blocks.php`; no icon if the theme has none). The text is edited in the block (bold and italic allowed); the URL (type one or search for a page) and an "Open in new tab" toggle are in the sidebar. Without text or a URL it outputs nothing. Markup only: style it in `components/_button-link.scss`.
  - `experience` is one job as an `<article class="experience two-column">` with two `.column`s: the date range on the left; on the right a heading (Heading 3 by default; 2–4 in Settings) with the position and company, separated by a decorative `·` that screen readers hear as "at", then the description (bold and italic allowed) and the tags as a `<ul aria-label="Skills">`. Tags are added in the sidebar (type and press Enter). Empty parts are left out; with no position, company or description it outputs nothing. Markup only: style it in `components/_experience.scss`.
  - `menu` is a `<nav>` with a list of links you manage in its sidebar: add, reorder and remove items, each with text, a URL (type one or search for a page by name; picking a page fills in empty text) and an "Open in new tab" toggle. It replaces WordPress's Navigation block and its separate menu screens: the items are stored in the block itself. The link for the page being viewed gets `aria-current="page"`. Items without text or a URL are skipped. "Menu name" (default "Menu") is the `aria-label`; give each menu on a page a different one. Used inside Sticky Left Side and usable anywhere else.
  - `projects` is a list (`<ul class="projects__list">`) of portfolio entries picked in its **Portfolio entries** panel (add from a search box; drag or use the arrows to reorder; remove). Each item has a thumbnail shown at 136×114 from a 272×228 cropped image, so it's sharp on retina screens (image size `joevernazza-project`, registered in `inc/portfolio.php`; existing uploads need `wp media regenerate --only-missing`) (the entry's Featured image, else its first Desktop slider image; decorative, `alt=""`), the title as a heading (Heading 3 by default) followed by `//` and the brand name when set, the excerpt (else the content) cut to 100 characters at the last whole word with "…" (50 below tablet width: both copies are output, `span.projects__excerpt-full` and an `aria-hidden` `span.projects__excerpt-short`, switched in `components/_projects.scss`; both lengths adjustable in Settings), and a "View Project" **Button Link** block (rendered by the Projects block: `div.button > a.button__link` with the arrow icon) to the entry's page whose screen-reader name includes the title. Unpublished or deleted entries are skipped. The editor shows a server-rendered preview. Markup only: style it in `components/_projects.scss`.
  - `page-pagination` is the previous/next project links on a portfolio entry, before `<main>` in the `single-portfolio` template: `div.page_pagination` with `p.page_pagination__prev`/`__next` > `a.page_pagination__link` (`rel="prev"`/`"next"`), each the theme's `assets/images/prev-btn.png`/`next-btn.png` (decorative) with screen-reader text naming the project. The order (`joevernazza_portfolio_sequence()`) is the home page's Projects block list, then any other published entries by Order field and date, looping at the ends. Outside a portfolio entry it outputs nothing. Markup only: style it in `components/_page-pagination.scss`.
  - `portfolio-slider` shows the current portfolio entry's slider images; it's in the `single-portfolio` template. It reads the entry from block context (`postId`), and its editor script adds the entry's **Slider images** sidebar panel (`panel.js`): add, reorder and remove slides, each with Desktop, Tablet and Mobile images. Each slide is a `<figure>` with a `<picture>` from `joevernazza_slide_picture()` (Desktop and Tablet as `min-width` sources, Mobile as the `<img>`) and the Desktop image's caption. Without JavaScript the track is a swipeable, keyboard-scrollable strip; with `view.js` the slides are stacked (`--stacked`, the current one `.active`) and change by screen width: below 1024px they slide in from the right (0.6s) and you swipe left/right (`--slide-x`), from 1024px they cross-fade with no swipe (`--fade`); the movement is CSS in `components/_portfolio-slider.scss`. They play automatically every 3 seconds and loop; the arrow keys also change them (no buttons, no pause button). It waits while the pointer is over it or focus is inside it, and doesn't play for reduced-motion users. Slides the user picks are announced. With no slides it outputs nothing. Front-end styles are in `components/_portfolio-slider.scss`.
  - `sticky-left-side` is the site header: a `<header>` with a headline, a title, a rich-text paragraph, a **Menu** block (locked in place between the text and the social icons; select it to edit its items; labelled "Main") and a repeatable list of social icon links, output inside the Menu's `<nav>` after its `<ul>` (`nav.menu > ul.menu__list + ul.sticky-left-side__social`, with a hamburger right before the `<nav>`: the [Hamburgers](https://github.com/jonsuh/hamburgers) "slider" type (`button.hamburger.hamburger--slider.sticky-left-side__toggle`; npm `hamburgers`, built in `global/_hamburgers.scss` with only that type, sized and colored there), hidden on desktop; below it, `initMenuToggle()` in `navigation.js` opens and closes the menu (`.is-active` on the button turns it into an X, `.active` on the nav, `aria-expanded`; Escape or choosing a link closes it); the `<nav>` starts with `div.mobile-header`, a copy of the block's own headline and title, as on the home page even on portfolio entries (same tags and classes, `aria-hidden` so they're not heard twice; hidden on desktop); last in the header when there's no menu; the editor still shows it after the menu). It lives in the `sticky-left-side` template part, before `<main>`, so it's the page's banner landmark and the skip link jumps past it. The headline is the `<h1>` on the front page and on portfolio entries; on other pages it's a paragraph, so each page keeps one `<h1>` (its own title). The title is always a paragraph (`p.sticky-left-side__title`). On a portfolio entry the headline, title and text are the entry's title, brand name and content (with its role, `p.sticky-left-side__role`, after the brand when set) (each content `<p>` gets `sticky-left-side__text`) instead of the block's own copy, under a "Back to projects" link (`p.very-small.sticky-left-side__back > a.sticky-left-side__back-link` with a decorative `img.sticky-left-side__back-icon` (the theme's `assets/images/arrow.svg`); text and URL in the block's **Portfolio pages** panel, default `/#projects`), with the entry's Launch links after the content as Button Links (`div.sticky-left-side__launch > div.button > a.button__link` + `img.button__icon`, opening in a new tab; nothing when the entry has none). The brand (`p.sticky-left-side__title`), role and Launch links show in the header on desktop only; below desktop a copy of each (built by the same helpers, `joevernazza_portfolio_role_html()` / `joevernazza_portfolio_launch_html()` in `inc/portfolio.php`) is put around the entry content, each in a `div.main__details` (the brand and role right before it, the Launch links right after it) (a `render_block_core/post-content` filter on the `.main__text` Post Content block), hidden on desktop. Each social link has an icon (any Media Library image, or pasted SVG code, which wins and is printed inline so CSS can color it: cleaned by `joevernazza_sanitize_svg_markup()` in `inc/svg-uploads.php`, with `aria-hidden` and the class `sticky-left-side__social-svg`; both are decorative), a tooltip and a URL. The link's `aria-label` is the tooltip (or the URL's domain) plus "(opens in a new tab)" when it does, so it keeps its name even if CSS hides the tooltip; the visible tooltip is `aria-hidden`. Links without a URL aren't shown. Social links open in a new tab by default (a toggle). The "sticky" positioning is front-end CSS in `components/_sticky-left-side.scss`; a tooltip shown on hover should also show on keyboard focus.

## Running locally

**Requirements:** Docker, Node.js 22+, Composer.

```bash
docker compose up -d          # WordPress -> http://localhost:8090, phpMyAdmin -> http://localhost:8091
cd build_tools
npm install
npm run watch                 # rebuild on save, with live reload
```

On a fresh clone, core is already in `public_html/`; `docker compose up` writes the local config and opens the installer. Then activate the **Joe Vernazza** theme, create a Home page, set it as the homepage (Settings → Reading), and set permalinks to **Post name**. Or run `scripts/pull-db.sh` to copy production.

Docker sets `WP_ENVIRONMENT_TYPE` to `local`, so analytics never load. WP-CLI: `docker compose run --rm cli wp <command>`.

## Database

Local runs **MySQL 8.4**, chosen to match production. Keep the engine and major version the same as the server, and update `image:` in `docker-compose.yml` if production is upgraded.

The database scripts run SQL through the database container's own `mysql` / `mysqldump` tools, so they always match the server version. For an SQL shell: `docker compose exec db mysql -uroot -proot joevernazza`, or use phpMyAdmin.

WP-CLI's `wp db` commands (`export`, `import`, `query`, `cli`, `reset`) only work against **MariaDB 11.4 or newer**. The WP-CLI image ships MariaDB's latest client tools, which require TLS: MySQL 8 rejects them, and older MariaDB servers don't offer TLS. Every other WP-CLI command, including `search-replace`, works normally because it goes through PHP like WordPress does. The scripts above work with any engine and version.

## Accessibility

The target is **WCAG 2.2 Level AA**. What's built in:

- **Structure:** `header` (Sticky Left Side, with its Menu `nav` labelled "Main"), `main` and `footer` landmarks, one `h1` per page, and core's "Skip to content" link. The theme moves keyboard focus onto `<main>` when the skip link is used, so screen readers announce the jump.
- **Keyboard:** a 2px focus ring on every link, button and field (white on dark backgrounds), and a skip link that's visible when focused. The Menu block has no mobile toggle: its links stay visible and reachable with Tab at every width.
- **Color and text:** the editor is limited to the theme palette, whose text colors meet AA contrast. Links are underlined. Font sizes are fluid and relative, so text resizes to 200%.
- **Targets:** menu items, the menu buttons and buttons are at least 44px tall (WCAG 2.5.8 asks for 24px).
- **Motion:** scroll-reveal content is visible without JavaScript. Reduced-motion settings turn off animations and smooth scrolling.
- **Forced colors:** focus rings, buttons and separators stay visible in Windows High Contrast.
- **Accessibility statement:** the footer links to a page with the slug `accessibility` when one is published. Publish one before launch, stating the target, what's done, known limitations and how to report a problem.

**Testing:** `npm run test:a11y` in `build_tools/` loads every published page, plus search and 404 results, at desktop (1280px) and mobile (375px) widths. It runs axe-core with the WCAG 2.0/2.1/2.2 A and AA rules, then checks the skip link, the focus ring, and that the header Menu's links are visible and focusable at mobile width. It exits non-zero on any problem. The first run needs `npx playwright install chromium`. ESLint also applies `jsx-a11y` rules to block code.

Automated tests only catch some accessibility issues. Before launch, also test with a screen reader (VoiceOver: Cmd+F5) and the keyboard alone, zoom to 200%, and check that every image has meaningful alt text (or empty alt if it's decorative).

## CI/CD

[`.github/workflows/deploy.yml`](.github/workflows/deploy.yml) lints every push and pull request (PHPCS, ESLint, Stylelint). On `main` it then builds and `rsync`s WordPress core, the theme and the must-use plugin to the server. `--delete` is scoped to `wp-admin/`, `wp-includes/` and our own folders, and `wp-config.php` is excluded, so the server's config, `.htaccess`, uploads and other plugins are never touched.

**Updating WordPress:** automatic updates are off. Locally run `docker compose run --rm cli wp core update` (then `wp core update-db`), test, check `wp core verify-checksums`, commit and push. After a deploy that changes the database version, visit wp-admin once so WordPress runs its database update.

**Repository secrets:** `SSH_PRIVATE_KEY`, `SSH_HOST`, `SSH_PORT`, `SSH_USER`, `DEPLOY_PATH` (the WordPress root on the server, the folder that contains `wp-content`).

## Production setup

1. Create the database and `wp-config.php` in `DEPLOY_PATH`, then import the local database (search-replaced to the live URL). Core arrives with the first deploy; don't run the installer.
2. Apply [`config/wp-config-production.sample.php`](config/wp-config-production.sample.php): `WP_ENVIRONMENT_TYPE` = `production`, debug off with logging outside the web root, `DISALLOW_FILE_EDIT`, `DISALLOW_FILE_MODS`, automatic updates off, `FORCE_SSL_ADMIN`, and a real cron job.
3. Push to `main` to deploy (core, theme and plugin), then check the theme is active.
4. Settings: allow search engines, use Post name permalinks, set the homepage, and add a Site Icon (the theme's SVG favicon is used until then).
5. Turn on page caching that suits the host (for example LiteSpeed Cache on LiteSpeed servers).
