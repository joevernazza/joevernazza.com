# Joe Vernazza

The source for [joevernazza.com](https://joevernazza.com): a custom WordPress block theme, a must-use plugin for site behavior, custom blocks, a Vite build, coding standards in CI, and deploys that only ship our own code.

## How this site was built

This repository was generated by **`wordpress-install`**, a reusable [Claude Code](https://claude.com/claude-code) skill I built with Claude Code. Instead of setting up each new WordPress project by hand, the skill turns one well-built site into a template. A single command then produces a new project with the same theme architecture, tooling, accessibility setup and deploy pipeline, already installed and running in Docker.

### Where the skill came from

1. **Static page.** joevernazza.com started as a single hand-written PHP page, with SCSS and JavaScript compiled by Vite.
2. **WordPress rebuild.** I rebuilt it on WordPress to show how I build WordPress sites properly. It started from Twenty Twenty-Five and was reworked into a custom pages-only block theme plus a must-use plugin, with the improvements listed below.
3. **Generalized into a skill.** The finished build was turned into a template, with the site name, slug, PHP prefix, URLs, ports, PHP version and database engine as placeholders. A Node script (`create-site.mjs`, no npm dependencies) fills them in and installs everything.
4. **Reinstalled from the skill.** This repo was then cleared and rebuilt from the skill, keeping the git history, so the site you see is exactly what the skill produces.

### What the install did

```bash
node create-site.mjs --dir joevernazza.com --name "Joe Vernazza" \
  --slug joevernazza --prefix joevernazza --tagline "Senior Front-End Developer" \
  --prod-url https://joevernazza.com --gtm GTM-XXXXXXX \
  --php 8.4 --db mysql --db-version 8.4 --port 8090 --pages-only
```

1. Copied the template and filled in the placeholders. It removes code for features that weren't chosen, and fails if any placeholder is left unfilled.
2. Ran `npm install` and `npm run build` (Vite for theme assets, `@wordpress/scripts` for blocks), and `composer install` for PHPCS.
3. Pulled the Docker images and **pinned each one by digest** in `docker-compose.yml`, then started the containers.
4. Used WP-CLI to install WordPress, then:
   - activated the theme and removed Akismet, Hello Dolly and extra default themes;
   - set Post-name permalinks and wrote the caching rules to `.htaccess`;
   - created the Home, About, Contact and Accessibility pages from the theme's patterns, and the Main menu.
5. Checked that the homepage renders with no PHP errors.
6. Ran the accessibility test (axe-core, WCAG 2.2 AA, desktop and mobile, plus keyboard checks). It passed with no violations.

### Adjustments made along the way, and why

Each of these came from building and testing this site. They now live in the template, so every future project starts with them.

**Architecture**

| Change | Why |
| --- | --- |
| Moved the Vite build into `build_tools/`, writing into the theme's `assets/` | Keeps Node tooling out of the web root and out of deploys. The theme gets plain, fixed-name CSS/JS files that `functions.php` enqueues, versioned by file modification time so each build busts the cache. |
| Replaced Twenty Twenty-Five with a custom theme (own prefix and text domain, only five templates, own patterns, no stock style variations) | A renamed default theme isn't a custom theme. Removing about 100 unused patterns and templates makes the code small enough to read and maintain. |
| Removed the full-page patterns (Home, About, Contact, Accessibility) and kept only section patterns | Any full-page pattern makes WordPress open a "Choose a pattern" screen every time a page is added. Pages here are built from sections, so the screen only got in the way. |
| Moved site behavior into a **must-use plugin** | The theme handles presentation and plugins handle behavior. A must-use plugin can't be deactivated, so security, SEO and pages-only mode survive a theme switch. |
| **Pages-only mode**: posts, comments, feeds, pingbacks and their admin screens are removed | This is a brochure/portfolio site. Leftover blog features add attack surface (comment spam, pingbacks, XML-RPC), clutter the admin, and leak empty archives and feeds to search engines. |
| Design tokens in `theme.json`, with SCSS reading WordPress's generated CSS custom properties | One source of truth, so the editor and the front end can't drift apart. Editors can only pick palette colors, which keeps contrast in check. |
| Custom blocks are built with `@wordpress/scripts` and registered from the plugin | It's WordPress's own block toolchain. The blocks are dynamic (`render.php`), so changing their markup later never triggers "invalid block" errors in the editor. |
| **Site Settings** screen (Head, Header, Footer) and a dynamic **Site Info** block for the footer | Site-wide values such as the GTM ID, verification tags, contact details and social links are edited in the admin, not in code. That keeps the GTM ID out of the repo and lets content changes skip a deploy. All fields are declared in one list, which drives the screen, the sanitizing and the storage. The footer shows the values through a block that renders on every request, so they stay current even after the footer is edited in the Site Editor. |
| The header finds the Main menu by its slug (`main-menu`), not by post ID | Menu IDs differ on every site and every database. Looking it up by slug works on any install, and the header falls back to a page list if the menu is missing. |

**Repository and deployment**

| Change | Why |
| --- | --- |
| Git tracks only the theme and must-use plugin; core, `wp-config.php` and uploads are ignored | Core is reinstallable, credentials don't belong in git, and uploads are content. Locally, the WordPress Docker image copies core in on first start. |
| The deploy `rsync`s only our two folders, with `--delete` limited to them | Removed files disappear from the server, but core, `wp-config.php`, uploads and other plugins can never be overwritten or deleted by a deploy. |
| Lint runs before every build (PHPCS with WordPress Coding Standards, ESLint, Stylelint), and on pull requests too | Coding standards are enforced, not just recommended, and a lint failure blocks the deploy. |
| Docker images are pinned by digest | Every machine runs exactly the same versions until someone deliberately updates them. |
| A sample production `wp-config.php` and `pull-db.sh`/`pull-uploads.sh` scripts | Environment settings stay on the server, documented. Content flows production → local, and code flows git → production. |

**Server parity**

| Change | Why |
| --- | --- |
| PHP 8.4 locally and in CI | It matches the production server, so nothing behaves differently after deploy. PHPCS still checks compatibility down to PHP 8.1, keeping the code portable. |
| MySQL 8.4 LTS, not 8.0 | It matches production, and MySQL 8.0 reached end of life in April 2026. |
| Database scripts use the database container's own `mysql`/`mysqldump`, not `wp db` | WP-CLI ships MariaDB's client tools, which require TLS and can't log in to MySQL 8. I tested relaxing MySQL's login and TLS settings, and the client still refused. Using the server's own tools always matches its version. (MariaDB was tried along the way too; the skill supports both, via `--db`.) |
| The install checks the database through PHP `mysqli` | That's the connection WordPress itself uses, so the check works on every engine and version. |

**Security and SEO**

| Change | Why |
| --- | --- |
| XML-RPC off, file editors off, REST user enumeration hidden, one login error message for every failure, security headers | These close the common WordPress attack paths a small site doesn't need. |
| The pages-only redirect runs before core's canonical redirect | Testing found that `/?author=1` first redirected to `/author/<username>/`, leaking the admin login. Running first sends it straight to the homepage. |
| A lightweight SEO module (meta description from the page excerpt, Open Graph tags, JSON-LD) that steps aside if an SEO plugin is installed | It covers the essentials without a heavy plugin, and won't output duplicate tags if one is added later. |
| Browser caching rules are written into `.htaccess` between their own markers | Core manages its rewrite rules the same way, so the rules survive permalink flushes and can be updated by bumping a version number. |

**Accessibility (WCAG 2.2 AA)**

| Change | Why |
| --- | --- |
| The skip link moves keyboard focus onto `<main>`, not just the scroll position | `<main>` isn't focusable by default, so focus stayed on `<body>` and some screen readers didn't announce the jump. The automated keyboard test caught this. |
| A 2px focus ring on every control (white on dark backgrounds), plus forced-colors support | Visible focus is required (WCAG 2.4.7/2.4.11), and the ring needs 3:1 contrast against whatever it sits on, including in Windows High Contrast. |
| Menu items and buttons are at least 44px tall, using a selector specific enough to beat core's navigation CSS | This exceeds WCAG 2.5.8's 24px minimum. The first version lost to core's more specific selector, which left the focus ring misaligned. |
| Scroll-reveal content is visible without JavaScript, and reduced motion turns off animation and smooth scrolling | Content never depends on a script running or on motion people have asked to avoid. |
| An automated accessibility test (`npm run test:a11y`) that runs on every install, and a footer link to an Accessibility statement page when one is published | The test runs axe-core on every page at two widths, plus keyboard checks, so regressions surface immediately. The statement tells visitors the target and how to report problems. |

## Architecture

**The theme handles presentation, plugins handle behavior.** Switching themes should change how the site looks, never what it does.

- **Theme ([`public_html/wp-content/themes/joevernazza`](public_html/wp-content/themes/joevernazza))**
  - `theme.json` is the single source of design tokens: color palette, the self-hosted Rubik variable font, a fluid type scale and spacing. SCSS reads the CSS custom properties WordPress generates from it.
  - Templates: `front-page`, `page`, `page-no-title`, `index` and `404`.
  - Header with the site title and the **Main** menu (a Navigation menu with the slug `main-menu`, edited in Appearance → Editor → Navigation). The footer links to the Accessibility and Privacy pages when they're published.
  - Section patterns in the "Joe Vernazza" category: Hero, Text section and Call to action. There are deliberately no full-page patterns: WordPress shows any full-page pattern in a "Choose a pattern" screen every time a page is added.
  - The **"Reveal on scroll"** block style on Group and Separator blocks fades a section's content in as it scrolls into view.
- **Must-use plugin ([`public_html/wp-content/mu-plugins`](public_html/wp-content/mu-plugins))**: always loaded, can't be deactivated, survives a theme switch.
  - `pages-only.php`: removes posts, categories, tags, comments, pingbacks and feeds from the admin, front end, sitemap and block inserter.
  - `security.php`: disables XML-RPC and the file editors, hides REST user enumeration, uses one login error message for any failure, and sends security headers.
  - `seo.php`: meta description (from the page excerpt), Open Graph/Twitter tags, `WebSite` JSON-LD. Steps aside if a full SEO plugin is installed.
  - `site-settings.php`: **Settings → Site Settings**, editable site-wide fields grouped as Head (GTM ID, Google/Bing verification, custom head code), Header (empty, ready for fields) and Footer (footer text, contact details, social links). Fields are declared once in `joevernazza_site_settings_fields()` (or the filter of the same name), which drives the admin screen, sanitizing and storage. Read values with `joevernazza_site_setting( 'key' )`.
  - `analytics.php`: Google Tag Manager, only when `WP_ENVIRONMENT_TYPE` is `production` and a container ID is set in Site Settings. A `JOEVERNAZZA_GTM_ID` constant in `wp-config.php` overrides it.
  - `htaccess.php`: browser caching and compression rules in `.htaccess`, between their own markers.
  - `blocks.php`: registers every block built into `joevernazza/blocks/`.
- **Blocks ([`build_tools/src/blocks`](build_tools/src/blocks))**: one folder per block, built with `@wordpress/scripts`. Every block wraps its contents in an inner `<div class="container">`, which is a styling hook with no CSS of its own (see [`docs/blocks-and-markup.md`](docs/blocks-and-markup.md)).
  - `section` wraps any blocks in `<section>` + `.container`. It has only an HTML anchor (id) and custom classes, set in the Advanced panel.
  - `site-info` shows Site Settings values (footer text, contact details or social links). The footer uses it so values stay current even after the template is edited in the Site Editor: a dynamic block renders on every request, while PHP inside a pattern only runs once.
  - `circular-cta` is a circle with rich text (bold, italic, strikethrough, sub/superscript). With a URL, the whole circle is one link and links inside the text are removed, since nested links are invalid HTML. Without one, the text can contain its own links. Options: three sizes, palette colors, font size, alignment, open in new tab.
  - `callout` is an example dynamic block (`render.php` + inner blocks). Copy it to start a new one.

WordPress core, `wp-config.php`, uploads and third-party plugins are **not** in git. Locally, the WordPress Docker image copies core into `public_html/` on first start. On the server, they're managed there.

## Running locally

**Requirements:** Docker, Node.js 22+, Composer.

```bash
docker compose up -d          # WordPress -> http://localhost:8090, phpMyAdmin -> http://localhost:8091
cd build_tools
npm install
npm run watch                 # rebuild on save, with live reload
```

On a fresh clone, `docker compose up` copies WordPress core in and opens the installer. Then activate the **Joe Vernazza** theme, create a Home page, set it as the homepage (Settings → Reading), and set permalinks to **Post name**. Or run `scripts/pull-db.sh` to copy production.

Docker sets `WP_ENVIRONMENT_TYPE` to `local`, so analytics never load. WP-CLI: `docker compose run --rm cli wp <command>`.

| Command                      | What it does                                          |
| ---------------------------- | ----------------------------------------------------- |
| `npm run build` (build_tools) | Production build of theme assets and blocks          |
| `npm run watch` (build_tools) | Rebuild on save, with live reload                    |
| `npm run lint:js` / `lint:css` | ESLint / Stylelint (WordPress configs)              |
| `npm run test:a11y` (build_tools) | axe-core WCAG 2.2 AA scan of every page + keyboard checks (`A11Y_URL=` to test another site) |
| `composer lint` / `lint:fix` | PHPCS: WordPress Coding Standards + PHP 8.1+ compatibility |
| `scripts/pull-db.sh`         | Copy the production database to local (asks first)    |
| `scripts/db-export.sh`       | Back up the local database to `db/`                   |
| `scripts/db-import.sh <file>` | Replace the local database with a dump (asks first)  |
| `scripts/pull-uploads.sh`    | Copy production media to local                        |

The scripts read SSH details from `.env` (copy [`.env.example`](.env.example)). Content flows **production → local**. Code flows **git → production**.

## Database

Local runs **MySQL 8.4**, chosen to match production. Keep the engine and major version the same as the server, and update `image:` in `docker-compose.yml` if production is upgraded.

The database scripts run SQL through the database container's own `mysql` / `mysqldump` tools, so they always match the server version. For an SQL shell: `docker compose exec db mysql -uroot -proot joevernazza`, or use phpMyAdmin.

WP-CLI's `wp db` commands (`export`, `import`, `query`, `cli`, `reset`) only work against **MariaDB 11.4 or newer**. The WP-CLI image ships MariaDB's latest client tools, which require TLS: MySQL 8 rejects them, and older MariaDB servers don't offer TLS. Every other WP-CLI command, including `search-replace`, works normally because it goes through PHP like WordPress does. The scripts above work with any engine and version.

## Accessibility

The target is **WCAG 2.2 Level AA**. What's built in:

- **Structure:** `header`, `nav` (labelled "Main"), `main` and `footer` landmarks, one `h1` per page, and core's "Skip to content" link. The theme moves keyboard focus onto `<main>` when the skip link is used, so screen readers announce the jump.
- **Keyboard:** a 2px focus ring on every link, button and field (white on dark backgrounds), and a skip link that's visible when focused. The mobile menu is a modal that traps focus, closes on Escape and returns focus to its toggle.
- **Color and text:** the editor is limited to the theme palette, whose text colors meet AA contrast. Links are underlined. Font sizes are fluid and relative, so text resizes to 200%.
- **Targets:** menu items, the menu buttons and buttons are at least 44px tall (WCAG 2.5.8 asks for 24px).
- **Motion:** scroll-reveal content is visible without JavaScript. Reduced-motion settings turn off animations and smooth scrolling.
- **Forced colors:** focus rings, buttons and separators stay visible in Windows High Contrast.
- **Accessibility statement:** the footer links to a page with the slug `accessibility` when one is published. Publish one before launch, stating the target, what's done, known limitations and how to report a problem.

**Testing:** `npm run test:a11y` in `build_tools/` loads every published page, plus search and 404 results, at desktop (1280px) and mobile (375px) widths. It runs axe-core with the WCAG 2.0/2.1/2.2 A and AA rules, then checks the skip link, the focus ring and the mobile menu from the keyboard. It exits non-zero on any problem. The first run needs `npx playwright install chromium`. ESLint also applies `jsx-a11y` rules to block code.

Automated tests only catch some accessibility issues. Before launch, also test with a screen reader (VoiceOver: Cmd+F5) and the keyboard alone, zoom to 200%, and check that every image has meaningful alt text (or empty alt if it's decorative).

## CI/CD

[`.github/workflows/deploy.yml`](.github/workflows/deploy.yml) lints every push and pull request (PHPCS, ESLint, Stylelint). On `main` it then builds and `rsync`s the theme and must-use plugin to the server. `--delete` is scoped to our own folders, so core, `wp-config.php`, uploads and other plugins are never touched.

**Repository secrets:** `SSH_PRIVATE_KEY`, `SSH_HOST`, `SSH_PORT`, `SSH_USER`, `DEPLOY_PATH` (the WordPress root on the server, the folder that contains `wp-content`).

## Production setup

1. Install WordPress in `DEPLOY_PATH` with a non-default table prefix.
2. Apply [`config/wp-config-production.sample.php`](config/wp-config-production.sample.php): `WP_ENVIRONMENT_TYPE` = `production`, debug off with logging outside the web root, `DISALLOW_FILE_EDIT`, `FORCE_SSL_ADMIN`, minor-only core auto-updates, and a real cron job.
3. Push to `main` to deploy, then activate the theme.
4. Settings: allow search engines, use Post name permalinks, set the homepage, and add a Site Icon (the theme's SVG favicon is used until then).
5. Turn on page caching that suits the host (for example LiteSpeed Cache on LiteSpeed servers).
